# ADR 0015: Hosted AI egress is a server policy that is off by default; speech-service hardening; what V2.1 closed and what it left to governance

- **Status:** accepted and implemented in slice V2.1 (the hardening step after V2, `9dfcca1`). It completes the part of [ADR 0012](0012-local-first-ai-hosted-providers-opt-in.md) item 4 ("setting a key alone enables nothing") for the existing hosted language-model steps, and records the disposition of the findings of the V2 security review ([ADR 0014](0014-local-speech-service-and-capture-pipeline.md)).
- **Date:** 4 Oct 2026

## 1. Hosted AI egress

### Context

After V2, consultation audio never leaves the computer, but "Generate draft", AI recommendations, Mana summaries and photograph descriptions are Anthropic-backed and switched themselves on whenever `ANTHROPIC_API_KEY` was present. On the development machine that key is present. A key in `.env` is a credential, not a decision to send patient data to a third party.

### Decision

- **One policy, one place.** `ai.egress.hostedProviders` in `config/adaxai.yaml` (committed, default **`false`**), overridable by the environment variable `AI_EGRESS_HOSTED` (`true` allows it on purpose; `false` forbids it whatever the file says; empty or unset: the file decides). The effective value is part of the settings snapshot whose hash is stored on every AI job.
- **A hosted provider is constructed only when egress is allowed AND a key is set** (`providersFromConfig`, the single place a hosted client is built). With egress off the drafter, recommender, image describer and Mana summariser do not exist, so they cannot be called by any route, retry or flag; each step says so ("Hosted AI processing is switched off on this server, so no consultation text leaves this computer…") instead of producing placeholder output. The existing provider abstraction and the Anthropic implementation are kept for controlled evaluation: nothing was deleted.
- **No fallback in either direction.** Speech is local only (no hosted adapter exists). The important-points extractor is the local rule set; a hosted extractor exists only if `ai.extraction.provider: llm` is chosen *and* egress is allowed, and with egress off that choice means "unavailable", not "use the rules" and not "use the hosted model". Allowing egress does not move extraction off the local rules.
- **The browser can only look.** `/api/ai/status` carries `egress: { hosted, destination }` (the host text would go to, only when allowed and a key exists) and never a key. No route changes a setting; a request flag such as `includeLlm` cannot widen what the server built. Administrators additionally see whether a key is configured on the server (a boolean) so an unused key is visible.
- **The screens say it.** The assistant panel shows "Hosted AI: off" with "Nothing leaves this computer" or, when allowed, "Hosted AI: allowed (to <host>)" with the disclosure that transcript text (name, MRN and phone removed, best effort) goes to a service that is not on this computer and that audio is never sent. The administrators' page shows the same and whether a key sits unused.
- **Tests** (`apps/api/test/egress.test.ts`, 13) use a loopback stand-in for the provider that **counts requests**, a placeholder key and no real provider: key present + egress off = **0 requests** through the real application (draft, recommendations with `includeLlm: true`, extraction, status); the same calls with egress on **do** reach the stand-in (the control); rules extraction stays local with egress on; a down speech service with a key and egress on never reaches the provider; no route lets any role (or nobody) change the setting; the status and the administrators' overview contain no key. The end-to-end suite allows egress only to its loopback mock and asserts that none of a capture's words reach it.

### Exact configuration

| To | Do this |
| --- | --- |
| Keep everything local (default) | Nothing. `ai.egress.hostedProviders: false` and no `AI_EGRESS_HOSTED`. A key may stay in `.env`; it is not used |
| Allow hosted AI on this server, on purpose | In `.env` set `ANTHROPIC_API_KEY=…` **and** `AI_EGRESS_HOSTED=true` (or set `ai.egress.hostedProviders: true` in `config/adaxai.yaml`), then restart the API. Each use still needs the patient's `ai_recording` / `ai_record_assistant` / `ai_image_analysis` consent and the doctor's click |
| Forbid it whatever the file says | `AI_EGRESS_HOSTED=false` |
| Point at a local stand-in for evaluation | `ANTHROPIC_BASE_URL=http://127.0.0.1:<port>` plus the two lines above (this is what the end-to-end suite does, with a mock) |

**Behaviour change for the development machine:** its `.env` has a key, so the development app now shows drafting, AI recommendations, Mana summaries and photo descriptions as unavailable until the owner sets `AI_EGRESS_HOSTED=true`. Whether to allow it for real consultations is a governance decision (below).

## 2. The speech service (a localhost sidecar), hardened

**Deployment assumption, stated plainly:** `services/speech` is a *sidecar of one API process on one computer*. It has **no sign-in on purpose**: a password or token that lives in a file next to it, on the same machine, would protect nothing and would only look like security. What protects it is that it **is not reachable from anywhere else**: it binds to loopback only (the launcher refuses another address unless `SPEECH_ALLOW_NON_LOOPBACK=1` is set deliberately), answers only requests addressed to a loopback host name (a web page cannot reach it through a DNS name it controls), asks for a client header that browsers cannot send cross-origin without a pre-flight the service never answers, and receives an allow-listed environment. **If a deployment ever needs the service on another machine, it needs a network boundary and real authentication (for example mutual TLS) that do not exist; that is a new design, not a setting.** Any process on the same computer, and any user who can run one, can call the service.

V2.1 added:

- **The content decides, not the name or the declared type.** Uploads are accepted only if their first bytes are one of WebM, Ogg, WAV, MP3 or MP4/M4A **and** that matches the declared type. The API refuses anything else with 415 before storing it; the service refuses it again (`415 unsupported_media`). A text file, playlist, concat list, image or script is "not audio" however it is named.
- **The demuxer is chosen by us.** The container is opened with the one FFmpeg demuxer for the sniffed kind and a protocol whitelist of in-memory data only, so an upload (for example a playlist that names an internal URL or a file) cannot make the service open a file or a network address. The service's request path makes no network access and none happens at inference time; the only code in the service that uses the network is the model download script (`app/fetch_model.py`), which a person runs on purpose (`npm run speech:model`) and which checks every file against the pinned hash.
- **A bound before the expensive work.** A duration the container declares is checked first; a container that declares none (a streamed WebM) is decoded in a stream that stops and refuses (`413 too_long`) the moment more than `SPEECH_MAX_AUDIO_SECONDS` (default 3,600 s) has come out. The audio is never decoded to the end and then measured. Malformed audio is `422`, never a crash.
- **Request limits, applied before the body is read.** A guard in front of the application (a pure ASGI middleware) refuses a declared length over the limit without reading a byte, cuts off a body that declares none (or lies) at the limit, and **counts a request from the moment it arrives**, so a burst of large uploads is refused with 429 instead of being held in memory or, past the multipart parser's memory limit, spooled to a temporary file (the review of V2.1 found the first version counted only after the whole body had been parsed; fixed and tested with a parser spy and a check that nothing reaches the temporary directory). Upload size 64 MB in the service (the API's own limit stays at `uploads.audio.maxMb`); at most 4 requests, each up to about 65 MiB, are in memory at once; at most `SPEECH_MAX_PENDING` (default 4) requests are being served or waiting at once, beyond which the service answers `429` with `Retry-After` (the API treats it as retryable); the API now rate-limits per signed-in user, by settings `security.rateLimits.aiAudioPerUser` (60 a minute) for audio parts and uploads and `aiStepPerUser` (30 a minute) for drafts, important points and recommendations, with the first refusal audited.

**Still true:** decoding hostile audio is done by FFmpeg (through PyAV) in a process with the permissions of the user who started it and no sandbox; a vulnerability in FFmpeg is outside what these controls can prevent, and they limit rather than remove the exposure. A file with a valid signature and a malformed body still reaches the (bounded) decoder.

## 3. Migration 0025, the seed, and withdrawal

- **Migration 0025** creates a unique index (one live recording per consultation). It **was not edited** (the runner refuses edits to applied migrations). It is applied and its index present in the development, test and end-to-end databases, none of which has a consultation with several live recordings (checked read-only). On a database that an earlier application version left with several, the migration would fail **atomically** (each migration runs in one transaction; nothing half-applied). A follow-up migration cannot help there (it runs after 0025), so the migration runner now has a **pre-flight check** (`apps/api/src/db/preflight.ts`) that says in words what is wrong and that nothing was changed, and a named, explicit, counted remedy: `npm run db:migrate -- --target <db> --end-duplicate-live-recordings` ends all but the newest live recording of each consultation (their transcript lines are kept). Tested on real rows in a rolled-back transaction and on the runner with a stand-in client (`preflight.test.ts`). Acceptable for the prototype because the condition arises only from the V1 application's abandoned recordings and the remedy is explicit.
- **The hospital seed no longer depends on the wall clock.** Its today's-appointments sit at offsets from the clinic's time of day, down to 150 minutes ago, and failed (overlapping slots, or a no-show that had not started) in the first hours after midnight and late in the evening. The seed now allocates overlap-free slots on the right side of "now", and in the first hours of the day (before 02:40) makes today's schedule as if it were midday, holding the clock the API reads for the whole run. The same holds late in the day: a booking 90 minutes ahead cannot be placed after "now" from about 23:15, so the seed also holds the clock at midday after 22:25. A session made while the clock is held starts at the held time, which **the seed sets itself** (an UPDATE through its own connection): the application's sign-in is **not** changed for it (the first version changed `createSession`, which the review rightly called a production change made for a tool). A `clinicMinute` option fixes the clinic time for tests; a time with no room for the schedule is refused (it never makes a booking that has already started). The real-clock path is unchanged between 02:40 and 22:25. Tested at 00:00, 00:30, 00:55, 02:00, 02:39, 03:20, 12:00, 22:25 and 23:00 explicitly, and with the real clock faked to 22:26, 23:15, 23:30 and 23:55.
- **Withdrawal** ends any live recording in the same step (audited) and the screens say what it does not delete: see [safety/CAPTURE_DATA.md](../safety/CAPTURE_DATA.md). Everything that stores audio checks the consent again at the last moment: an uploaded recording after its body has arrived (the first version checked only before reading it, which for a 25 MB upload over a slow link is a long window), the start of a live recording in the step that creates it, and each part in the step that stores it. Those steps read the consent **under a lock** (`FOR SHARE`), and a withdrawal updates it, so the two cannot pass each other: either the step commits first (and the withdrawal then ends what it created) or the withdrawal commits first (and the step is refused, its bytes removed). Tested with a real slow upload, a withdrawal during the speech service's health check, and a withdrawal that is made to wait for a step that holds the lock (each fails if the check or the lock is removed).

## 4. Disposition of the V2 security-review findings still open

### FIX NOW (done in V2.1, with tests)

Hosted egress policy (and the screens' statements of it, which follow whether a hosted client exists, not whether drafting is available); the screens' statements about where speech-to-text runs (this computer, or the host the clinic pointed it at); audio content sniffing (API and service); the request-body cap and early counting; duration bound before decoding; demuxer choice and protocol whitelist; per-user rate limits on audio and costly steps; service request limits (size, concurrency, 429); migration 0025 pre-flight and explicit remedy; server-side end of live recordings on withdrawal and a plain statement of what withdrawal does not delete; the hospital-seed time-of-day failure (early and late); the egress disclosure on screen.

### DOCUMENTED PROTOTYPE LIMITATION

- The speech service has no sign-in (a deliberate deployment assumption above); anything on the same computer can use it.
- Hostile-audio decoding is unsandboxed FFmpeg under the user's account; a signature check does not prove a file is well-formed.
- A part lost after the browser's four retries is a transient warning and leaves no gap marker after a reload; a live transcript abandoned by a closed tab is ended by withdrawal, by the next start (stale replacement) and by the recorder, but **not** by signing or discarding the consultation.
- Very long recordings: the transcription call times out at 180 s (reported as a timeout) and the segment cap is 5,000 lines.
- Pseudonymisation of text for hosted AI is best effort (registered name, MRN and phone number only).
- Rate limits are per process and in memory (a restart resets them); the speech service's own cap is a counter, not a queue with fairness.
- Packages are pinned by version, not by hash.

### REQUIRES A CLINICAL / LEGAL / GOVERNANCE DECISION (not decided here)

Whether hosted AI egress may be turned on for real consultations at all, and under what agreement; retention periods; erasure on request or on withdrawal (and how that reconciles with append-only clinical and audit records); encryption at rest and what backups may contain; who may read captured audio and transcript text and the facility-wide AI review list; the consent wording (a legal and clinical-governance review). See [safety/CAPTURE_DATA.md](../safety/CAPTURE_DATA.md) §4.

## Consequences

- Drafting, AI recommendations, Mana summaries and photo description are **unavailable by default**, including on the development machine; tests and demonstrations that need them set the environment variable on purpose.
- The development stack that was already running before V2.1 must be restarted to load the new rules (the API, the speech service and the web app).
- ADR numbers 0013 to 0015 on the secondary-apps branch collide with `main`; whoever merges second renumbers.
